## Readiness closure

The P0 defect was a split failure boundary. Frozen PROCESS could commit a new
document epoch while Coordination-side route, graph, child, cursor, or barrier
publication subsequently failed. Rollback could then restore an old `READY`
marker and make the newly committed state visible before its graph was safe.

The corrected state transition is:

```text
frozen PROCESS commits epoch N
    -> document remains CATCHING_UP
    -> routes and Process Embedded graph publish for epoch N
    -> child sessions, barriers, receipts, and parent cursors reconcile
    -> direct-boundary synchronization proof succeeds
    -> graphPublishedEpoch == readyEpoch == epoch N
    -> READY(N) publishes
    -> document() may return the current snapshot
```

`document()` independently checks the complete proof and fails with
`DOCUMENT_NOT_READY`; `auditDocument()` remains the explicit view of exact
committed but not-yet-ready state. Child commits use the reverse graph to mark
only lagging parents `CATCHING_UP`. Recovery repairs stale readiness and resumes
from receipts without repeating a committed frozen PROCESS call.

| Required proof | Result | Repeated frozen work |
| --- | --- | ---: |
| Committed parent plus graph-publication failure remains non-readable | `PASS` | 0 parent PROCESS reruns |
| Child commit immediately makes lagging containing parents non-ready | `PASS` | 0 child PROCESS reruns |
| Restart normalizes recoverable stale readiness | `PASS` | 0 child replays |
| Every independent application-read prerequisite fails closed | `PASS` | 0 |

The independent read matrix covers ready epoch, graph-published epoch, barrier,
pending admission, binding, cursor, child epoch, and embedded-BlueId mismatch.
The ordinary no-embedded-document path retains an allocation-light empty
boundary. A parent with `N` direct managed children performs `O(N)` readiness
work without scanning unrelated documents, Timelines, or the environment.

## Capability and blocker classification

The generic Timeline Entry model's missing universal literal `documentId` is an
optional generalized targeting-profile capability, not an engine blocker. The
environment derives recipients, one entry may target several managed
documents, and concrete Channel/message types can define exact target
derivation. Repository-native `OperationRequest.document` targeting remains
supported.

Provider-backed Mandate eligibility is different: it remains a real agentic
blocker until exact authority at the entry's source order can be resolved. It is
not inferred, emulated, or bypassed.

## Remaining limitations

- **In-memory:** verified only as a sequential, single-process engine.
