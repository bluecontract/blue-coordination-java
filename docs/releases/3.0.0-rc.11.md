## Decision

This baseline-reconciliation candidate is authorized for Maven Central
publication only after the exact Java 17 and Java 21 release gates complete
successfully. The markers declare the permitted release tier; they do not
record a completed build, passed test run, or published artifact. Readiness
must be established by fresh artifact-bound evidence for this candidate.

The public build must resolve this complete published tuple:

- Language and Contracts modules: `3.1.0-rc.27`;
- BEX core and contracts: `1.1.0-rc.6`;
- Repository: `3.0.0-rc.22`;
- Coordination: `3.0.0-rc.11`.

Language advances from RC25 to RC27; BEX and Repository retain the RC10
coordinates. Coordination directly owns the complete Language graph and
retains the BEX and Repository transitive exclusions in its generated POM.
The published dependency lock must bind that exact graph. Maven Local,
sibling source composites, invocation-owned development repositories, and
staged repository fallback cannot supply public release evidence.

## Changes since RC10

The [baseline reconciliation](../baseline-reconciliation-disposition.md) and
[correction record](../rooted-baseline-release-fixes.md) describe the retained
fixes and their regression owners. They cover exact authored/source views,
frozen historical admission endpoints, source-epoch and same-epoch successor
evidence, legal later detached retargeting, join scheduling, fair bounded
drains, gas/transition accounting, and exact prerequisite observations.
Named Compute keeps the merged upstream implementation and adds exact
contribution-presence handling. Bounded complete-input eligibility memoization
is retained for the demonstrated restart acceptance case. Optional proof-copy,
cross-call representation memoization, and early LIVE-capture optimizations
remain omitted. The C03 nested/contextual identity family is entirely deferred.

The final publication transition selects released Language RC27 and advances
release metadata to RC11; it adds no further runtime, specification, or gas
rule changes. Earlier development receipts retain their exact source and
artifact bindings and are not relabeled as published-tuple qualification.

## Supported profile and required evidence

The candidate retains the bounded, sequential, single-JVM runtime release tier
and rooted checkpoint processing. The complete current `releaseCheck` must
pass on Java 17 and Java 21, including unit, integration, built-JAR consumer
and scenario tests, dependency isolation, public API and publication checks,
structural test architecture, and an isolated build from the extracted source
archive. Production bytecode remains Java 17.

`verifyRcReadiness` retains the complete RC10 capability inventory. The release
workflow prepares one exact candidate and runs the full Java 17 staging gate
and Java 21 compatibility gate concurrently; publication waits for both
successful jobs and deploys only the verified Java 17 staged bytes after
comparison with the Java 21 built artifacts.

Only a successful current gate writes
`build/reports/release/3.0.0-rc.11-readiness.json` with freshly built artifact
hashes. Existing development exports and earlier RC receipts retain their
original meaning and do not certify this release.

## Explicit non-claims

- no authoritative Timeline-provider import or completeness contract;
- no Mandate or target-time eligibility implementation;
- no list-position identity for `Process Embedded.collectionPaths`;
- no import of arbitrary managed draft state through `ManagedDocumentDraft.atEpoch(...)`;
- no process-restart persistence supplied by Coordination itself;
- no distributed or multi-node durability, scheduling, or consensus;
- no production tenancy, authentication, operations, or stable latency SLA;
- no stable 3.0.0 API claim.

Applications must supply and verify their durable command, receipt, and
exact-content storage boundary. This candidate is intended for bounded
external pilots and local application integration.
