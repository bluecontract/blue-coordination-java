# Coordination specification traceability matrix

**Scope.** Every required conformance fixture in §25 of the Blue Coordination Specification 1.0 (candidate), traced to the implementation on `blue-coordination-java` branch `next` at commit `20fca9f` (3.0.0-rc.5) and, where behavior is delegated, to `blue-language-java` `origin/next` (3.1.0-rc.23).

**Method.** Each row was produced by reading the spec sentence and its section, then locating the main-code path and a test whose assertions check that behavior. Coverage was never inferred from a test or class name. Line numbers refer to the commits above and will drift.

**Status vocabulary.**

| Status | Meaning |
| --- | --- |
| COVERED | Main implements it and a test asserts it. |
| PARTIAL | Implemented but untested, tested for only part of the sentence, or tested only through an internal API. |
| DELEGATED | Coordination hands the behavior to the Contracts runtime; the handoff is cited. |
| FAIL-CLOSED | Not implemented, but the runtime deterministically rejects the input instead of silently accepting it. |
| MISSING | Not implemented and not rejected, or the concept does not exist in code. A row marked "contradicts" means the implementation does the opposite of the spec sentence. |

### Where the implementation contradicts the spec

These are not coverage gaps. The code does something the spec text forbids, and in several cases a test locks the behavior in.

1. **Checkpoint subject shape (55, 56, 57).** The subject is a projected `{semantics, timestamp, timelineBlueId, entryBlueId}` tuple plus a mandatory `domain`, which is exactly the "former shape" Appendix C retires. Contracts rc.23 `CheckpointEntry.blue` requires `domain`. §16.1, §16.3 and §30 are contradicted.
2. **Composite subjects embed member metadata (64).** `memberKey` and `memberDomain` are written into the subject; §16.7 says membership must not be handled that way.
3. **Readiness before catch-up (78).** `SdkAcceptanceTest.java:108-110` asserts `ready()` before imported history is drained, against §19.5. `ContractsJournalDrainCoordinator` scans from the global `processedThrough`, so history behind the environment frontier is never delivered, against §15.4.
4. **Timeline identity is a text pair (11, 18).** `ExternalOrderKey` and Timeline binding use `timelineId` text and `accountId`, not the exact Timeline BlueId required by §6.2, §7.3 and §9.2.
5. **Unnecessary `onBehalfOf` is rejected (47).** §13.3 says direct eligibility must ignore it.
6. **General messages are rejected at append (39).** §12.6 allows non-Operation events through Timeline Channels.
7. **Internal sources excluded by string prefix (88).** `RoutingSurface.java:258-262` filters on `coordination/internal/` rather than by exact type, against §20.1.
8. **No specification identity (1).** §3.2 requires every canonical Coordination type to reference the exact specification BlueId; nothing in the code, resources or the bundled type repository does.

## Family notes

### 25.1 and 25.2 Specification binding, Timeline and entry integrity

- No Coordination specification identity exists anywhere in main, resources, or the bundled type repository; fixtures 1, 3, 4 have no anchor, and closing them rotates every Coordination type BlueId.
- All entry-integrity rejections (predecessor, monotonic timestamp, Timeline binding) live in `InMemoryTimelineJournal.publish` / `WholeRequestEntryFactory.createExact`, but the only rejection tests target `TimelineProviderSupport` static helpers (`followsExactPredecessor`, `evaluateCompletenessWindow`) that main never calls. Nothing drives these rejections through `CoordinationEngine` or the SDK.
- Timeline identity is the `(timelineId, actorId)` text pair (`api/Timeline`), not the BlueId of the complete Timeline value; engine-built entries hard-code `MyOS/MyOS Timeline` and the actor type (`WholeRequestEntryFactory.java:259-263`), so concrete-type mixing is invisible to the journal.

### 25.3 and 25.9 Completeness, order and historical catch-up

### 25.4 and 25.10 Timeline Channels and other specifications

### 25.7 Checkpoints

- The whole checkpoint model on this branch (Coordination 3.0.0-rc.5 + Contracts 3.1.0-rc.23) is the pre-spec `domain + projected tuple` form: `CheckpointEntry.blue` requires `domain`, and Coordination's subject is the Appendix C "former shape". §16.1, §16.3 and §30 are contradicted, not merely untested. Fixtures 55-57 fail together, and closing them changes the Contracts `CheckpointEntry` type BlueId and every checkpoint YAML.
- Because the subject is inline, Appendix B's `RESOLVE_EXACT`/`NEEDS_RESOURCES` branch and Appendix C's `INVALID_CHECKPOINT_EVIDENCE` have no code path; `NEEDS_RESOURCES` in code means "closure needs exact values / provider unavailable", never "checkpoint subject unresolvable".
- Reset semantics (62-65) ride entirely on domain-BlueId inequality inside Contracts; Coordination never removes a checkpoint entry itself. No Coordination test reads `contracts/checkpoint/entries` after a removal, rebind, or re-add.
- Composite and All-Timelines subjects embed `memberKey`/`memberDomain`, the opposite of §16.7's "not by embedding member metadata into the subject".
- The retry/atomicity integration tests (`FailureRetryAtomicityTest`, `RetryStructuralCountersIntegrationTest`, `EmbeddedReceiptRetryIdentityIntegrationTest`, `WholeObjectFailureHygieneTest`) never mention checkpoints; they test managed-epoch cursors and receipts.

### 25.8 and 25.11 Feeder, topology, recovery and audit

- The spec's feeder vocabulary (§21.2) is only partially represented: `WITHHELD`, `DEFERRED_UNAVAILABLE`, `INVALID_EVIDENCE`, `UNSUPPORTED` do not exist as public dispositions; ineligibility is either thrown at append (`IllegalArgumentException`) or collapsed into `NO_MATCH`/`REJECTED`.
- All "crash" coverage is injected-exception based (`PublicationFailurePoint`, `MultiDocumentPublicationTransaction.FailurePoint`, `TestEngine.FailurePoint`) plus `restartFromStores()`; there is no durable persistence, so the restart boundary is the in-memory `DurableState` copies (`ContractsRootFeederWindow.java:393-426`). Durable Coordination (§24.5) is correctly not claimed.
- Provider completeness proof is bound to the embedded/temporal lane (`CatchUpBarrier`) but not recorded in Contracts-lane revisions or publication receipts, breaking the §23.1 chain at "verified completeness frontier and proof".
- Feeder correctness is pull-based; there is no notification abstraction, so §15.7 is satisfied by absence rather than by design or test.
