# Rooted historical attachment frontier

The rooted profile retains complete committed root views in publication order, each with the logical boundary of its authenticated input. Retained-history applications carry their original attachment barrier boundary; they cannot make a later boundary appear earlier. Full-history admission has its existing unbounded beginning, and bounded admissions retain their exact lower-exclusive order. Repeated representations remain separate retained positions; BlueId is not the history index.

When a known source is attached, automatic expansion selects its last retained view before the attaching input’s complete ExternalOrderKey. It carries that view’s exact body, forward bindings, component generations and subscription progress. A newer independent source head does not replace those inputs. Owned head/topology publication fences remain required. An immutable historical witness that needs a conflicting second value for an already-present DocumentId still fails closed pending the separate witness-role repair.

RCP-CAUSE-01/02 requires the historical interval to end at the semantic join anchor. Under this profile the planner therefore retains the selected source epoch and does not extend existing intervals when a later source revision is published. The old profile keeps its prior extension rules. The transaction checks the view’s asserted boundary against its exact original input or owning historical barrier before retaining it.

Production SDK checks prove that attachment at 200 imports only source inputs 100, 105 and 115, then processes the parent’s 250 input before source 500 as LIVE. This holds when source 500 was independently published before attachment or after the interval was created, with source receipts unchanged and restart preserving the interval. Intermediate assertions inspect the current audit state while keeping the previous valid Ready state visible. The unchanged acyclic five-successor test and 27 adjacent source/gas/order/planner/publication checks passed. Earlier/later view-boundary mutations are rejected by the publication verifier.

This is an implemented development slice, not release readiness.
